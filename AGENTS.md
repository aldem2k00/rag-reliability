# AGENTS.md — правила работы в этом репозитории

Читается агентом автоматически. Если тебе выдали ID задачи — открой `docs/handoff/tasks/<ID>.md`
и работай строго по ней. Общий контекст — `docs/handoff/HANDOFF.md`.

## Проект

Автоматический quality gate для русскоязычного банковского RAG-бота.
Вход: `(диалог + вопрос, до 8 retrieved-чанков, ответ бота)`.
Выход: `faithfulness ∈ {0,1}`, `relevance ∈ {0,1}`, `reliable = faith ∧ rel`.
Первичная метрика: macro-F1 по `reliable`. Ограничение: только локальные модели.

Корпус: 2233 уникальных кейса, 72.25% reliable, контекст ~2500 токенов медианно.

## Команды

```bash
make install        # uv venv + зависимости, ставит консольный скрипт rag-judge
make check          # тесты + ruff — ДОЛЖЕН быть зелёным перед PR
make test
make lint
pytest tests/test_foo.py -k some_case -x     # точечно
```

Python ≥ 3.11. Пакет — src-layout, `src/rag_reliability/`.

## Жёсткие правила

1. **Владение файлами.** Меняй только файлы из раздела «Владеет» своей карточки. Всё остальное read-only. Нужна правка в чужом файле — опиши её в PR в разделе «Требуется от других», но не делай.
2. **Никаких `dict.get(key, default)` для фич, скоров и вероятностей.** Отсутствие ключа — исключение с понятным сообщением. Молчаливый дефолт уже приводил к тому, что битая строка признаков трактовалась как «идеально надёжный кейс».
3. **Порог не подбирается на данных, на которых отчитываются.** Только на train-части фолда.
4. **Не вызывай `split_samples` в новом коде.** Разбиение читается из `data/splits/folds.json`. Исключение — регресс-тесты, воспроизводящие исторические числа.
5. **Не меняй сигнатуры из `HANDOFF.md` §7.** Кажется неверной — остановись и напиши в PR.
6. **Числа только с интервалами.** Любая метрика в отчёте сопровождается 95% ДИ.
7. **Тесты пишутся вместе с кодом.** Минимальный набор указан в карточке.
8. **Не добавляй новые варианты методов в реестр «про запас».**

## Стиль

- Имена, API, типы — английские. Комментарии и докстринги — можно русские, в репозитории смешанный стиль.
- Докстринг объясняет *почему*, а не пересказывает код.
- `from __future__ import annotations` в начале модулей.
- Типы обязательны в публичных сигнатурах.
- Ruff: конфигурация в `pyproject.toml`, не переопределяй.
- Ошибки — с контекстом: не `raise ValueError("bad input")`, а `raise ValueError(f"Missing predictions for {len(missing)} sample(s): {missing[:5]}")`.

## Планирование

Карточка `docs/handoff/tasks/<ID>.md` — это уже план. Не запускай
`superpowers:writing-plans` поверх неё: получится план плана, а планирующий агент
может незаметно пересмотреть решения, которые карточка фиксирует.

**Карточка владеет вопросом «что». План — только вопросом «как».**

Встроенный plan mode (Shift+Tab) оправдан, если изменение > 300 строк **и** в
карточке нет сигнатур на каждую функцию. Это задачи A1, B1, C2, C4 и, аккуратно,
B2. Для остальных планирование — накладные расходы.

Артефакты планов не коммитить в репозиторий: держи в `.plans/` (в `.gitignore`)
или вне репозитория.

Подробнее — `docs/handoff/PLANNING.md`.

## Тесты не должны закреплять баги

Прецедент: `tests/test_m3_logprobs.py:66-69` требовал, чтобы токен с P(PASS)=0.905
давал 0.475. Тест был зелёный, поэтому баг прожил через три ветки.

Когда пишешь тест на функцию, которую сам же реализовал, спроси: этот тест
проверяет **требуемое** поведение или просто фиксирует то, что получилось?
Для чистых функций предпочитай property-тесты (монотонность, калибровка,
инварианты) вместо примеров с захардкоженными ожиданиями.

- [ ] все критерии приёмки из карточки выполнены поимённо
- [ ] изменены только файлы из раздела «Владеет»
- [ ] в описании PR: что сделано, какие критерии закрыты, что требуется от других задач

## Сомнения

Если карточка противоречит коду или спецификации — не угадывай. Опиши противоречие
в PR и реализуй наиболее консервативный вариант (тот, что не меняет чужие контракты).
