# Волна 2 — итог слияния и статус выхода

Ветка `integration`, слияние B1 → B2 → B3 в указанном порядке.
`make check` прогонялся после каждого мержа.

**Итог одной строкой:** волна 2 влита, код зелёный, измерительный контур
работает end-to-end — но **выход из волны 2 закрыт наполовину**: регресс на
десяти числах воспроизводится, а `report.json` для `surface`/`majority` собрать
нельзя. `evaluate_cv` требует покрытия всех 2233 кейсов, OOF-метод структурно
даёт 1480. Волна 3 упирается в тот же барьер (C1, C2).

## 2. Что пришлось чинить интегратору

### 2.1 B3 снесла вход регресс-теста (4 упавших теста)

`predictions/alfa/baselines/{surface,majority}/scores.jsonl` занимала миграция
A3: 446 исторических кейсов с id `alfa_*`. Именно её читал
`test_protocol_regression.py` — единственный вход, на котором старые числа
воспроизводимы. B3 записала туда OOF-прогон, и десять чисел стали
невоспроизводимы.

Причина не в B3 как таковой: `scores.jsonl` — это **текущий** артефакт метода,
его перезаписывает любой прогон, а вход регресса обязан быть замороженным.
Один путь обслуживал две несовместимые роли.

Сделано: миграция A3 вынесена в `scores_legacy.jsonl` для всех **пяти**
опубликованных прогонов, а не только для двух пострадавших — в волне 3 те же
пути перезапишут C2 (`encoder`), C3 (`m3`), C4 (`m6`). Добавлен
`test_legacy_scores_stay_frozen_on_historical_ids`: подмена входа теперь падает
на входе (446 строк, префикс `alfa_`, покрытие обоих сплитов), а не проявляется
расхождением итоговой метрики.

### 2.2 B3 и B2 работали не на том корпусе

Волна 2 унаследовала два взаимоисключающих корпуса:

| Корпус | Строк | Схема id | Фолды | Кто ввёл |
|---|---:|---|---|---|
| `data/organizers.jsonl` | 2245 | `organizer_NNNNNN` (номер строки, без дедупликации) | `folds.json` | A1 |
| `data/alfa.jsonl` | 2233 | `alfa_<sha1>` (контентный) | `folds_alfa.json` | B1 |

Пересечение пространств id **пусто**. Все опубликованные артефакты и все
опубликованные числа живут на `alfa_*`; B1 канонизировала этот корпус явно
(`scripts/prepare_alfa_corpus.py`), пометив, что берёт территорию A1
вынужденно. B2 (`independent`) и B3 (`surface`, `majority`) этого не увидели и
скорили `organizers.jsonl` — их артефакты нельзя было сопоставить ни с одним
опубликованным числом.

Сделано: все три перепрогнаны на каноническом корпусе. Числа §3 получены на нём.

**Решение по A1 vs B1 не принято и остаётся за людьми.** Интегратор выровнял
артефакты по канону B1, потому что иначе не воспроизводились десять чисел, —
но `data/organizers.jsonl` и `folds.json` в репозитории остались, и
`run_surface_baseline.py` по-прежнему указывает на них в дефолтах `--data` /
`--folds`. Пока это не разрешено, любой новый прогон по умолчанию попадёт не в
тот корпус.

### 3.2 Первая честная таблица на новом протоколе

5×5 CV по `folds_alfa.json`, порог подбирается внутри train-части фолда,
метрика считается один раз по склеенным OOF-решениям. n = 1480 оцениваемых
кейсов из 2233, base rate 0.7250.

| Метод | macro-F1 (reliable), OOF | 95% ДИ | полуширина | ROC-AUC |
|---|---:|---|---:|---:|
| `surface` | **0.5350** | [0.5102, 0.5615] | ±0.0257 | 0.5571 |
| `independent` | **0.5122** | [0.4866, 0.5382] | ±0.0258 | 0.5204 |
| `majority` | **0.4757** | [0.4528, 0.5007] | ±0.0240 | 0.5016 |

Парное сравнение `surface` vs `majority`: Δ = **+0.0594**, ДИ [0.0230, 0.0959],
p = 0.0020 — значимо. Единственное, что пока значимо превышает базовую ставку.

**Главный измеримый результат фазы 0.** Полуширина ДИ для `surface` упала с
**±0.0703** (старый единичный holdout на 223 кейсах) до **±0.0257** — в 2.7 раза;
для `m3 zero_shot` старая была ±0.0700. Ради этого фаза 0 и делалась.
Оговорка: у `majority` старая полуширина была ±0.0215, то есть уже, чем новая
±0.0240 — константный предсказатель не выигрывает от роста выборки, у него
дисперсия и так вырожденная. Сравнение честно только для методов с сигналом.

**Второй результат — числа поехали вниз, как и ожидалось.** Опубликованный
`surface` — 0.6133 val / 0.5982 test; leak-free OOF — 0.5350. Разрыв ≈0.06
складывается из старого сплита с 24.9% утечкой и оценки на 223 кейсах.
`surface` из карточки C1 (0.6218) на новом протоколе не существует: абляционную
таблицу C1 придётся пересчитать, и правило включения фичи может отсечь то, что
раньше проходило.

## 5. Незакрытые критерии

### 5.1 Блокер: `evaluate_cv` и OOF-методы требуют несовместимого

```
ValueError: predictions/alfa/baselines/surface/scores.jsonl is partial:
1480 of 2233 corpus case(s) scored, 753 missing ...
```

- `require_full_coverage` (`scripts/evaluate_cv.py:178`, B1) требует строку на
  **каждый** кейс корпуса. Обоснование B1 верное: иначе состав кейсов становится
  свойством того, докуда дошёл прогон.
- `folds_alfa.json` (A1) исключает oversized-группу `grp_daea0b19de2e` —
  **753 кейса, 33.7% корпуса**. Предсказать их out-of-fold нечем.
- Значит **ни один OOF-метод никогда не пройдёт эту проверку**: ни `surface`,
  ни `majority`, ни `encoder` из C2, чей критерий приёмки прямо требует
  «`enc.logit` по всем 2233».

Две «partial» — разные вещи, и код их не различает: прогон, который не дошёл
(отвергать надо), и кейсы, которые оценить нельзя структурно (отвергать нечего).
B3 уже пишет это различие в `run.yaml` секцией `coverage`
(`corpus_n`/`scored_n`/`excluded_n`/`reason`), но `evaluate_cv` её не читает.

Варианты (решение за владельцами B1/A1, интегратор не выбирал):

1. Сверять покрытие с `corpus ∩ folds.assignment`, а не с корпусом. Дёшево;
   `evaluate_cv` и так отбрасывает неназначенные кейсы (`n_excluded`), то есть
   сейчас требуются данные, которые заведомо выбрасываются.
2. Пересмотреть решение A1 об oversized-группе: треть корпуса вне оценки — это
   вопрос сам по себе, а не следствие.
3. Оставить как есть и признать, что `report.json` существует только для
   не-OOF методов. Тогда C1 и C2 нужно переписывать в критериях приёмки.

Пока не решено — **волна 3 стартует с заблокированной оценкой для C1 и C2.**

### 5.2 `sd_across_repeats` для surface/majority измеряет ноль

`run_surface_baseline.py` усредняет OOF-вероятности по 5 повторам **внутри**
артефакта. На выходе — одна вероятность на кейс, поэтому `evaluate_cv` видит
один и тот же скор во всех повторах: `per-repeat F1 sd = 0.0000`,
`threshold sd = 0.0000`. Повторы в `folds_alfa.json` действительно различаются
(проверено), но до метрики эта вариативность не доходит.

Диагностика разброса по жребию — одно из обоснований 5×5 CV, и для этих двух
методов она сейчас пустая. Либо артефакт должен нести скор на каждый повтор,
либо диагностику надо помечать как неприменимую.

### 5.3 Дефолты CLI указывают на неканонический корпус

`scripts/run_surface_baseline.py`: `--data data/organizers.jsonl`,
`--folds data/splits/folds.json`. Прогон без явных флагов молча уедет на корпус,
id которого ни с чем не сходятся. Правка тривиальная, но файл принадлежит B3, а
выбор корпуса — открытый вопрос §2.2.

2233. Перепрогон `m3` требует GPU (задача 0.6), `encoder` — C2.
`m6_selfcheck` и `encoder` остаются `corpus_wide=False`.
