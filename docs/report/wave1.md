## 2. Вмешательства интегратора

Все три — швы между корректно выполненными задачами, не выход агентов за границы
владения. Матрица HANDOFF §6 была проверена по каждому: **ни один агент не
изменил файл вне своей колонки.** A5 правил `docs/experiments.md`, которого нет
в матрице, но он явно перечислен в карточке `docs/handoff/tasks/A5.md` §Владеет.

**(a) `build:` пин `ruff>=0.4,<0.15`.** `make check` был красным **на базовой
`integration` до любого мержа** — 119 ошибок. Причина не в коде: ruff 0.16.0
расширил набор правил по умолчанию (RUF100 ×58, EXE001 ×22, B008 ×9 и т.д.).
Версии 0.8.6 / 0.12.12 / 0.14.4 дают `All checks passed!` на неизменённом дереве.
Без верхней границы `make check` не является сигналом. A1 независимо зафиксировал
то же наблюдение в своём PR (121 диагностика).

**(b) удалён `tests/test_prepare_splits.py`.** Файл проверял CLI-контракт
`--output-dir` с трёхчастным стратифицированным сплитом — тем самым, который
спека §1 удаляет как источник утечки 24.9%. Держать его зелёным = держать
утечку. Замена — `tests/test_splits.py` (A1), 10 тестов нового CLI, включая
`--check` и детект подделки `assignment`/корпуса. **Файл не входил ни в одну
колонку матрицы:** A1 владеет `tests/test_splits*.py`, что не покрывает
`test_prepare_splits.py`. A1 поступил правильно, не тронув его, и честно
отметил провал в PR.

**(c) пути `predictions/**` в 5 тестах A2/A3/A4.** A5 владеет переносом каталогов,
A2/A3/A4 владеют своими тестами, шов не закреплён ни за кем. Правки механические,
по карте переносов A5: `local→alfa`, `alfa_openrouter→alfa`, `cloud→pseudo_debug`.

### Дефект матрицы владения (для волн 2–4)

Матрица закрепляет модули, но не связки «модуль ↔ его существующий тест» и
«переезд файла ↔ ссылки на него». Оба раза это дало красный `make check` у
дисциплинированного агента. Перед волной 2 стоит добавить правило: **агент,
меняющий контракт файла, владеет и всеми существующими ссылками на него**, либо
явно перечислять такие файлы в карточке.

### 3.1 Блокирующий дефект: `folds.json` построен на неканоническом корпусе

**Пересечение id между `folds.json` и всеми 16 мигрированными артефактами = 0.**

Две несовместимые схемы id:

| Источник | n | id |
|---|---:|---|
| `data/organizers.jsonl` → `folds.json` | **2245** | `organizer_000001` … (номер строки, `scripts/prepare_data.py:110`) |
| `predictions/**` и все опубликованные числа | **2233** | `alfa_9b24723685d8` … (контентный хэш) |

`data/organizers.jsonl` — **предканонический снапшот до дедупликации.**
Проверено: 2245 сырых строк содержат ровно **12 дубликатов** по
`(question, context, answer)`; 2245 − 12 = **2233** — канонический счёт из
README и спек.

Схема канонического id найдена в **другом** репозитории —
`skol/src/rag_reliability/data/alfa_loader.py:20`:

```python
def make_case_id(dialog: str, answer: str) -> str:
    digest = hashlib.sha1((dialog + "\x00" + answer).encode("utf-8")).hexdigest()
    return "alfa_" + digest[:12]
```

Воспроизведение по `question + "\x00" + answer` из `data/organizers.jsonl` даёт
**422 из 446** id артефакта surface (94.6%); остаток — расхождения нормализации
в конвертере CSV→jsonl. То есть корпус тот же, канонизации нет.

Это же объясняет аномальную oversized-группу на **759 кейсов (33.8% корпуса)**,
из-за которой A1 выбросил треть данных: near-dup-группировка по недедуплицированным
строкам слипает дубликаты в один блок. На каноническом корпусе группа будет
существенно меньше, а `excluded_ids` — заметно ниже 759.

Вины A1 здесь нет: карточка указывала `data/organizers.jsonl`, единственный
корпус в репозитории. Канонизирующего загрузчика в этом форке **не существует** —
`scripts/prepare_data.py` присваивает номера строк, а поддержка CSV в нём помечена
как TODO, при том что сырые данные лежат как `from_organizators/data/data.zip`
(`data.csv`, 30 МБ).

## 4. Что блокирует волну 2

### 4.1 Жёсткий блокер: B1 `evaluate_cv` нечего оценивать

B1 реализует `evaluate_cv(samples, predictions, folds, ...)` и обязан
воспроизвести 10 опубликованных чисел (критерий 6). При нулевом пересечении id
он либо упадёт на «нет предсказаний для 1486 кейсов», либо — что хуже — вернёт
пустую агрегацию. Запускать B1 до починки корпуса бессмысленно.

**Требуется до старта волны 2** (задача уровня A1, не B1):

1. Канонизирующий загрузчик в этом форке: `data.zip` → дедуп по
   `(question, context, answer)` → `alfa_` + sha1(dialog `\x00` answer)[:12] →
   2233 кейса. Ориентир — `skol/src/rag_reliability/data/alfa_loader.py`.
2. Разобрать 24 из 446 несовпадающих id (нормализация в конвертере).
3. Перегенерировать `folds.json` на каноническом корпусе, перепроверить
   `leak_check`, `excluded_ids` и oversized-группу.
4. Перепроверить критерии 2 и 3 на новых числах.

Пока это не сделано, критерии 1–3 держатся на числах, посчитанных не на том
корпусе, и **не могут считаться закрытыми**.

### 4.2 Мягкие блокеры

- **CI отсутствует полностью.** `.github/` в репозитории нет, ни одного workflow.
  Критерий 1 требует проверки сплитов в CI; критерий также подразумевает, что
  `make check` кто-то прогоняет автоматически. Владельца у `.github/` в матрице
  нет — нужно назначить.
- **Критерий 7 закрыт наполовину.** `MetricWithCI.null_percentile` объявлен
  `float | None`; чтобы отчёт «без `null_percentile` не собирался», поле должно
  быть обязательным. Это правка `schema.py`, то есть A3, а не B1. Иначе
  B1/B2 начнут собирать отчёты без калибровки по шуму — ровно то, от чего
  критерий защищает.
- **Критерий 8 требует GPU.** Полные прогоны m3/m6 на 2233 кейса — этап
  DataSphere (HANDOFF §1). Но surface-бейзлайны считаются на CPU и могут быть
  перепрогнаны сразу после починки корпуса; это даёт часть из «минимум 6 методов».
- **759 исключённых кейсов** (33.8%) при сохранении после канонизации сузят CV
  до 1486 кейсов вместо ~2100, на которые спека §8 рассчитывала ширину ДИ ±0.022.
  Ожидаемый эффект фазы 0 в этой части не будет достигнут — стоит перепроверить
  порог `oversized` после канонизации.
