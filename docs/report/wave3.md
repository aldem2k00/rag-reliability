# Волна 3 — итог слияния, числа и решения

Ветка `integration`, слияние C2 → C4 → C3 → C1 в указанном порядке.
C1 влит последним намеренно: стэк должен был увидеть сигналы, появившиеся в C2/C4.
`make check` прогонялся после каждого мержа.

**Итог одной строкой:** волна 3 влита, код зелёный (607 passed, 1 skipped, ruff clean),
оба критерия выхода формально закрыты — но **закрыты они одним и тем же сигналом,
что и в волне 2**. Стэк даёт 0.6543 только за счёт `m3.p_faith` на когорте 331 кейса
из 2233; единственный новый сигнал волны (M6-grounding) не прошёл отбор по ДИ, а два
других (энкодер, LettuceDetect) не появились вовсе — C2 отложила прогон до GPU.
Решение по ветке M6 принято: **закрывается как ветка развития** (§4).

### 1.1 Что пришлось чинить интегратору

**C4 вернула сентенизацию на `razdel`, но зависимость не добавила.** Карточка C4 не
даёт агенту `pyproject.toml`, поэтому PR честно вынес пункт в «Требуется от других» и
закрыл свои собственные тесты `importorskip`-ом. После мержа это дало 14 упавших
тестов: `features.py` импортируется из `test_m6_method`, `test_m6_pipeline`,
`test_prepare_m6_features` и CLI-смоуков `test_m6_grounding`, а там `importorskip`-а
нет и не должно быть.

Сделано: `razdel>=0.5` добавлен в **core**-зависимости (коммит `37225c7`), а не в
extras `m6`. Обоснование — `features.py` лежит на пути CPU-тестов и `score.py`;
extras `m6` тянет torch и transformers, ставить их ради чистого Python-сентенизатора
неправильно. В ветке `m3-m6` `razdel` тоже был в core.

C1 при этом влился без единой правки — ровно потому, что шёл последним.

## 2. Критерии выхода из волны 3

| Критерий (`HANDOFF.md` §10) | Статус |
|---|---|
| стэк ≥ 0.62 macro-F1 на 5×5 CV | ✅ **0.6543** (точечная оценка) |
| σ между повторами < 0.02 | ✅ **0.0092** |
| у M6-grounding есть первый ROC-AUC | ✅ **0.548 [0.522, 0.575]** для `m6.min_entail`, n = 2233 |
| `make check` зелёный | ✅ 607 passed, 1 skipped, ruff clean |

Оба содержательных критерия закрыты по букве. Три оговорки, без которых число 0.6543
читается неправильно:

1. **Когорта — 331 кейс из 2233 (14.8%).** Её задаёт пересечение источников: `m3
   zero_shot` покрывает 446 кейсов, `surface_e5` — те же 446, фолды оставляют 331.
   Это не тот масштаб, на котором мерялась волна 2 (1480).
2. **Нижняя граница 95% ДИ — 0.5956, то есть ниже порога 0.62.** Критерий
   сформулирован на точечной оценке и на ней выполнен; правило П3 («ни одного числа
   без интервала») требует показать, что интервал порог не подтверждает.
3. **Критерий закрыт старым сигналом.** Из трёх фич, ради которых волна 3 и делалась,
   в стэк не вошла ни одна: `enc.logit` и `ld.max_unsup` недоступны (артефактов нет),
   `m6.*` доступны и отобраны не были. Финальный набор фич совпадает с тем, что C1
   получила до волны: `surf.p_faith`, `surf.p_rel`, `m3.p_faith`.

### 3.3 Чего волна 3 не дала

| Задача | Что отложено | Причина |
|---|---|---|
| C2 encoder | вся таблица из 7 конфигураций, `enc.logit` на корпусе | GPU в сессии не было |
| C2 encoder | вердикт «длинный контекст вредит» — не снят и не подтверждён | прежний вывод построен на схлопнувшемся прогоне (`recall = 1.0`) |
| C3 m3-axes | все числа «после»: разделение осей, self-consistency, criteria injection | vLLM не поднимался; код проверен на dummy-бэкенде |
| C1 stacking | `enc.logit`, `ld.max_unsup` в абляции | артефактов нет |

Три задачи из четырёх написали код и не получили чисел. Это ровно то распределение,
которое `HANDOFF.md` §1 и предсказывал («GPU нужен для *запусков*, не для *написания*»),
но означает оно вот что: **волна 3 не проверила ни одной своей гипотезы, кроме M6.**

## 4. Решение по ветке M6

Правило из `docs/handoff/tasks/C4.md`, раздел «Правило принятия решения по ветке»:

| Полоса ROC-AUC (`m6.min_entail`) | Предписание | Факт |
|---|---|---|
| ≥ 0.60 и нижняя граница ДИ > 0.55 | фича идёт в стэк, ветка развивается | не выполнено: 0.548, нижняя граница 0.522 |
| 0.53–0.60 | проверить альтернативные NLI-модели и агрегации | **это наш случай** |
| ≤ 0.53 и верхняя граница ДИ < 0.57 | закрыть количественно | не выполнено: 0.548 > 0.53, верхняя граница 0.575 > 0.57 |

**Решение: ветка M6 закрывается как направление развития. Задач M6 в волне 4 нет.**

Основание — предписание средней полосы выполнено и исчерпано:

1. **Альтернативная NLI-модель проверена.** `Feudor2/rumodernbert-nli` даёт 0.556
   [0.529, 0.583] — внутри ДИ mDeBERTa. Путь «взять модель получше» пройден.
2. **Агрегации проверены все.** min / mean / max / доля ниже порога — в таблице §3.2,
   разброс 0.461…0.556, интервалы взаимно пересекаются. Лучшая (`mean_entail`, 0.556)
   от целевой (`min_entail`, 0.548) статистически неотличима.
3. **Стэк сказал «нет» по своему правилу.** Это решающий аргумент, а не третий по
   счёту: правило отбора C1 (нижняя граница парного ДИ приращения > 0) — то самое
   место, где вопрос «нужна ли фича» решается корректно. Все три M6-фичи дали
   отрицательное приращение с ДИ поверх нуля (§3.1).
4. **Динамического диапазона нет.** Медиана `m6.max_entail` = 0.997, медиана
   `m6.min_entail` = 0.751: почти у любого ответа находится хорошо подкреплённый
   источник. Это объясняет слабость сигнала и говорит, что дело не в модели.
5. **Coverage мёртв по мощности, а не по эффекту.** Целевые подгруппы —
   `reason_missed_chunk_conditions` n = 3 и `reason_incomplete_answer` n = 6 на 2233
   кейса. На таких n метод нельзя ни подтвердить, ни опровергнуть.

**Формулировка, которая должна попасть в отчёт проекта:** это закрытие *по исчерпанию
предписанной проверки*, а не по автоматическому срабатыванию нижней строки таблицы.
Точечная оценка 0.548 в полосу «закрыть количественно» не попадает. Честная запись —
«M6 даёт слабый, но ненулевой сигнал (AUC 0.548 [0.522, 0.575]), который не переживает
отбор в стэк; развитие остановлено, потому что предписанные картой способы его усилить
исчерпаны». Это защитимый негативный результат, и он таковым и подаётся.

**Что остаётся жить:**

- 12 фич `m6.*` на всех 2233 кейсах лежат в `predictions/alfa/m6_grounding/` и остаются
  доступны стэку. Если C2 доедет до GPU и `enc.logit` появится, стэк пересчитает
  абляцию заново — и M6-фичи в ней снова будут участвовать наравне;
- починки C4 (razdel, оконный NLI, softmax по {entail, contra} без neutral) — это
  исправления багов, а не M6-специфика; они остаются в `methods/m6/` и не откатываются;
- SelfCheckGPT остановлен ещё карточкой C4, до всяких измерений; это решение волна 3
  не пересматривала.

**Что решение НЕ означает:** оно не отменяет `semantic_entropy` как тему и не
утверждает, что grounding не работает в принципе. Оно утверждает ровно одно — на этом
корпусе, при 72.25% базовой ставке и такой доле хорошо подкреплённых ответов, ветка
не окупает следующего GPU-часа лучше, чем C2 и C3.
