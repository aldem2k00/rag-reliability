# PLANNING — нужен ли слой планирования поверх карточек

Короткий ответ: **карточки в `tasks/` уже занимают слот плана.** Прогонять
`superpowers:writing-plans` поверх них — значит писать план плана. Но для 4 задач
из 15 планирование оправдано, а для остальных — нет. Ниже правила.

---

## 1. Что уже сделано за вас

Формат `superpowers:writing-plans` и формат карточки решают одну задачу и
покрывают одни и те же разделы:

| writing-plans | карточка `tasks/<ID>.md` |
|---|---|
| Goal | «Проблема» + заголовок |
| Architecture / Tech Stack | «Что сделать» с сигнатурами |
| Global Constraints | `AGENTS.md` §«Жёсткие правила» + `HANDOFF.md` §7 «Контракты» |
| Files (Create/Modify/Test) | «Владеет» (плюс матрица владения в `HANDOFF.md` §6) |
| Task N → Steps с чекбоксами | «Что сделать» по пунктам |
| Testing guidance | «Тесты» |
| Definition of done | «Критерии приёмки» |

Разница одна: в карточках нет литерального кода на каждый шаг и нет TDD-чекбоксов
на уровне «напиши падающий тест → реализуй». Это осознанно: где решение
однозначно, литеральный код в плане экономит время; где есть свобода дизайна,
он её преждевременно убивает.

## 2. Почему лишний слой планирования опасен именно здесь

В вашем прошлом плане, в разделе Global Constraints, зафиксировано:

> Сплиты: `dataset.split_samples` (80/10/10, стратификация по reliable, seed 42)
> поверх `data/organizers.jsonl` — самосогласованно с остальным репо aldem

Это ровно тот протокол, под которым 24.9% тестовых строк делят вопрос с train, а
тривиальный 1-NN-запоминатель даёт 0.6278 macro-F1 — выше всех опубликованных
чисел проекта. Решение было принято по разумному соображению («согласованность с
репозиторием») и после этого **захардкожено в 1293 строки плана как ограничение**,
которое исполнитель не должен пересматривать.

Планирование не защищает от неверной посылки. Оно её укрепляет и распространяет.
Чем длиннее план, тем дороже потом пересмотр.

Отсюда правило: **карточка владеет вопросом «что», план — только вопросом «как».**
Если агент в режиме планирования начинает пересматривать решение из карточки
(два порога вместо одного, оставить semantic entropy, свой сплит) — это не план,
это регрессия. Останови и укажи на карточку.

## 3. Когда планировать, а когда нет

| Задача | Планирование | Почему |
|---|---|---|
| A1 splits | **да** | алгоритм группировки, oversized-группы, производительность на 2233² — несколько валидных дизайнов |
| B1 protocol | **да** | ядро контура, инварианты утечки порога, режим совместимости |
| C2 encoder | **да** | цикл обучения, OOF, контроль схлопывания, память под 8192 |
| C4 m6-grounding | **да** | шесть починок + два новых модуля, порядок важен |
| B2 score-cli | **осторожно** | высокий blast radius (реестр читают CLI, бенчмарк, демо) — план короткий, но нужен |
| C3 m3-axes | опционально | много писанины, но решения зафиксированы в карточке |
| D2 gepa | опционально | то же |
| A2, A3, A4, A5, C1, D1, D3, D4 | **нет** | механические или полностью специфицированы; план — чистые накладные расходы |

Ориентир: планируй, если изменение > 300 строк **и** в карточке нет сигнатур на
каждую функцию. Если сигнатуры есть — их достаточно.

## 4. Какой механизм

**Встроенный plan mode Claude Code** (Shift+Tab) — дефолт. План эфемерный, живёт
в сессии, утверждается перед первой правкой. Подходит, когда задача укладывается
в одну сессию — это все 15 карточек.

**`superpowers:writing-plans`** — когда работа заведомо не влезает в сессию или
план нужно показать человеку до исполнения. У вас это уже сработало: ветка
`feature/m3-m6-thresholds` — результат такого плана. Но:

- артефакты плана **не коммитить в репозиторий**. Вы это уже поняли на практике
  (`27282df Remove superpowers spec/plan docs from repo`, `033d91b chore: remove
  internal task report from branch`). Планы — процесс, а не продукт. Держите в
  `.plans/` из `.gitignore` или вне репозитория;
- план пишется **от карточки**, а не от исходной задачи. В промпте: «составь план
  реализации `tasks/A1.md`», а не «составь план group-aware сплитов».

**`superpowers:subagent-driven-development` / `dispatching-parallel-agents`** —
не нужны. Их роль — декомпозиция и параллелизация — уже выполнена матрицей
владения файлами в `HANDOFF.md` §6. Матрица строже: она гарантирует отсутствие
конфликтов по построению, а не по договорённости.

## 5. Что важнее планирования: независимая проверка

Главный риск при агентной реализации — не плохой план, а правдоподобная, но
неверная реализация, которая проходит собственные тесты.

Этот проект уже пострадал ровно от этого. Баг в `logprobs.py:77-80` (`sigmoid` от
логарифма вероятности) прожил через три ветки **потому что юнит-тест
`test_m3_logprobs.py:66-69` закреплял его как корректное поведение**. Агент,
пишущий и код, и тест, воспроизводит этот сценарий с высокой вероятностью.

Два механизма против этого, оба дешёвые:

**5.1. Регресс-тесты против реальных артефактов.** Заложены в карточки намеренно:

| Карточка | Что воспроизводится | Можно ли подделать |
|---|---|---|
| A2 | Δ = +0.0141, ДИ [−0.076, +0.105], p = 0.765 на закоммиченных предсказаниях | нет |
| A4 | устранение 11 расхождений `p` vs текстовый вердикт в `gepa_plain_s1/val.jsonl` | нет |
| B1 | 10 опубликованных чисел до 1e-6 в legacy-режиме | нет |
| C1 | macro-F1 ≈ 0.6085 и AUC ≈ 0.6277 на 446 кейсах | нет |

Эти числа посчитаны независимо и лежат в карточках. Агент не может их подогнать,
не реализовав задачу правильно. Это сильнее любого плана.

**5.2. Отдельный агент-верификатор.** После PR — второй агент, который кода не
писал:

```
Прочитай docs/handoff/tasks/A1.md и diff ветки task/A1-splits.
Проверь КАЖДЫЙ критерий приёмки отдельно, запусти команды проверки.
Отдельно: не закрепляет ли какой-нибудь тест неверное поведение
(прецедент — tests/test_m3_logprobs.py:66-69, где тест фиксировал баг).
Верни список: критерий → выполнен/нет → доказательство.
Ничего не исправляй.
```

Стоит одну сессию на задачу и ловит именно тот класс ошибок, который здесь уже
реализовался. Для A1, A4, B1, B2 — обязательно; для остальных — по желанию.

## 6. Итоговая схема

```
карточка tasks/<ID>.md          ← что делать (зафиксировано, не пересматривается)
    │
    ├─ 4 задачи: plan mode      ← как делать (A1, B1, C2, C4 + осторожно B2)
    │
    ├─ реализация + тесты
    │
    ├─ агент-верификатор        ← обязательно для A1, A4, B1, B2
    │
    └─ PR в integration
```

Планирование — точечный инструмент, а не обязательный этап. Верификация —
обязательный.
