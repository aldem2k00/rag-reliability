# SPLIT — распределение задач между Codex и Claude Code

Карточки агент-агностичны: интерфейс между исполнителями — PR в ветку `integration`.
Но два семейства агентов имеют разные ограничения, и от этого зависит, кому что отдавать.

---

## 1. Общий файл инструкций

Codex читает `AGENTS.md`. **Claude Code читает `CLAUDE.md`, а не `AGENTS.md`** — автоматического
фолбэка нет. Канонический файл один, второй его импортирует:

```
AGENTS.md      ← единственный источник правды (уже написан)
CLAUDE.md      ← две строки:

               @AGENTS.md

               (ниже — только Claude-специфичные дополнения, если появятся)
```

Симлинк (`ln -s AGENTS.md CLAUDE.md`) тоже работает, но ломается на Windows. Дублирование —
нет: разъедется на первой же правке.

## 2. Жёсткое ограничение Codex Cloud, которое определяет всё остальное

| Фаза | Интернет | Секреты |
|---|---|---|
| setup script | **есть** | доступны |
| работа агента | **нет по умолчанию** (можно включить limited/unrestricted) | **удалены перед стартом** |

Три следствия:

1. **Все зависимости ставятся в setup-скрипте.** Агент не сможет доустановить пакет.
2. **Задачи с живыми вызовами LLM в Codex Cloud не работают** — секреты удаляются до старта агента.
   Это исключает C3 (реальная проверка промптов), D2 (GEPA).
3. **Загрузка моделей с HF во время работы невозможна.** Либо предзагрузка в setup (тяжело),
   либо задача уходит в Claude Code локально. Это C2 (энкодер), C4 (NLI).

Codex CLI локально этих ограничений не имеет — если запускаете локально, разделение
можно делать только по пункту 3 ниже.

## 3. Разделение

**Codex — задачи, которые полностью офлайн, имеют жёсткие критерии и проверяются запуском тестов:**

| ID | Почему Codex | Что нужно в setup |
|---|---|---|
| A2 stats | чистые функции, числа для регрессии даны в карточке | numpy, scipy, scikit-learn |
| A3 schema | механическая: поле + валидатор + миграция | — |
| A4 logprobs | правка чистой функции, property-тесты, регресс на закоммиченных артефактах | `hypothesis` |
| A5 hygiene | перемещения файлов и правки текста, нулевая свобода дизайна | — |
| C1 stacking | только sklearn, целевые числа даны (0.6085 / 0.6277), артефакты в репозитории | scikit-learn |
| D1 perchunk | один модуль, dummy-бэкенд, без сети | — |

Общее у них: **самопроверяемость.** В каждой есть число или инвариант, который нельзя
подделать, не решив задачу.

**Claude Code — задачи со свободой дизайна, широким охватом или живыми моделями:**

| ID | Почему Claude Code |
|---|---|
| A1 splits | алгоритм группировки, обработка oversized-групп, производительность на 2233² — несколько валидных дизайнов |
| B1 protocol | ядро контура, инварианты утечки порога, режим совместимости |
| B2 score-cli | высокий blast radius: реестр читают CLI, бенчмарк и Gradio-демо |
| C2 encoder | цикл обучения, загрузка модели, GPU |
| C3 m3-axes | проектирование промптов под критерии организаторов — доменное суждение по русскому банковскому тексту |
| C4 m6-grounding | шесть починок в связке + загрузка NLI-модели |
| D2 gepa | DSPy, живые вызовы, протокол H5 |
| D3 notebooks | суждение про DataSphere, структура ноутбуков |
| D4 reporting | формулировки для статьи |

Итого 6 / 9. Волны сохраняются: волна 1 — Codex берёт A2, A3, A4, A5; Claude Code берёт A1.

## 4. Главная выгода двух семейств: перекрёстная верификация

Параллелизм — не самое ценное. Ценнее то, что **верификатор из другого семейства не разделяет
слепых пятен исполнителя.**

Проект уже пострадал ровно от одноимённого сбоя: баг `sigmoid(logprob)` прожил через три ветки,
потому что юнит-тест `tests/test_m3_logprobs.py:66-69` закреплял его как корректное поведение.
Агент, пишущий и код, и тест, воспроизводит это охотно; агент того же семейства при проверке —
с заметной вероятностью тоже.

Правило: **кто реализовал — тот не верифицирует.** Реализовал Codex → верифицирует Claude Code,
и наоборот.

Промпт верификатора:

```
Прочитай docs/handoff/tasks/<ID>.md и diff ветки task/<ID>-*.
Проверь КАЖДЫЙ критерий приёмки отдельно, запуская команды проверки.
Отдельно ответь: не закрепляет ли какой-нибудь новый тест неверное поведение?
Прецедент — tests/test_m3_logprobs.py:66-69, где тест фиксировал баг и тот прожил
через три ветки.
Верни таблицу: критерий → выполнен/нет → доказательство (вывод команды).
Ничего не исправляй.
```

Одна сессия на задачу. Обязательно для A1, A4, B1, B2 — они блокируют остальных.

## 5. Setup-скрипт для Codex Cloud

Файл `codex-setup.sh` в корне репозитория (или вставить содержимое в поле setup script):

```bash
#!/usr/bin/env bash
set -euo pipefail
python -m pip install --upgrade pip
pip install -e ".[dev]"
pip install hypothesis            # property-тесты для A4
python -c "import numpy, scipy, sklearn, pydantic; print('deps ok')"
make check
```

Замечания:

- `export` в setup не переживает переход к фазе агента — переменные окружения задавать через
  настройки окружения, не через скрипт;
- контейнер кэшируется до 12 часов; при смене зависимостей кэш надо инвалидировать;
- `make check` в конце setup даёт агенту заведомо зелёную отправную точку. Если он красный
  до начала работы — агент потратит сессию на чужие поломки.

## 6. Что удерживает единый стиль при двух семействах

| Механизм | Что покрывает |
|---|---|
| `ruff` из `pyproject.toml` + `make check` | форматирование, импорты, длина строк |
| `AGENTS.md` §«Стиль» | язык комментариев, типы, формат ошибок |
| `HANDOFF.md` §7 «Контракты» | сигнатуры, схема `folds.json`, формат артефактов |
| Матрица владения `HANDOFF.md` §6 | отсутствие конфликтов по файлам |

Этого достаточно. Дополнительных соглашений между агентами не требуется — они и не смогут
их согласовать, работая параллельно.

## 7. Порядок запуска волны при смешанном составе

```bash
bash docs/handoff/setup_worktrees.sh 1        # локальные worktree-ы
git push -u origin task/A2-stats task/A3-schema task/A4-logprobs task/A5-hygiene
```

- ветки для Codex Cloud **должны быть запушены** — он работает с удалённым репозиторием;
- A1 (Claude Code) идёт локально в своём worktree;
- A3 стоит влить первой: она фиксирует `Prediction.scores`, остальные делают `git rebase integration`
  после её мержа;
- после слияния волны — `make check` на `integration`, затем верификаторы по PR, затем следующая волна.

## 8. Чего не делать

| Не делать | Почему |
|---|---|
| Отдавать одну задачу обоим агентам «для сравнения» | получите два PR на одни файлы и ручной мерж; сравнивать надо реализацию с критериями, а не две реализации между собой |
| Давать Codex Cloud задачи с живыми вызовами LLM | секреты удаляются перед фазой агента |
| Разрешать агенту менять `AGENTS.md` | это общий контракт; правки — отдельным PR от человека |
| Запускать верификатор того же семейства, что и исполнитель | теряется главное преимущество смешанного состава |
