## Проблема

`src/rag_reliability/methods/m3/logprobs.py:77-80`:

```python
if lp_pass is None:
    return 1.0 - 1.0 / (1.0 + math.exp(-lp_fail))
if lp_fail is None:
    return 1.0 / (1.0 + math.exp(-lp_pass))
```

`lp` — логарифм вероятности, всегда ≤ 0 ⟹ `sigmoid(lp) ∈ (0, 0.5]`. Монотонность инвертирована в зоне уверенности:

| P(PASS) | logprob | текущий результат | верный |
|---:|---:|---:|---:|
| 0.999 | −0.0010 | **0.4997** | 0.999 |
| 0.9 | −0.1054 | **0.4737** | 0.9 |
| 0.1 | −2.3026 | 0.0909 | 0.1 |

Уверенный PASS бинаризуется в FAIL при любом пороге ≥ 0.5.

Подтверждено на артефактах: сверка записанного `p` с текстовым вердиктом по всем 22 файлам дала 64 расхождения, из них **61 со значением `p ∈ [0.49, 0.51]`**. Худший файл — `predictions/cloud/m3/gepa_plain_s1/val.jsonl`: 11 расхождений из 28.

**Тест `tests/test_m3_logprobs.py:66-69` закрепляет баг как корректное поведение** — поэтому он и прожил через три ветки.

## Что сделать

### 1. Исправить `_pass_prob`

```python
def _pass_prob(tok: Token) -> float:
    """P(PASS) в позиции вердикта.

    Обе стороны в top -> softmax по паре.
    Видна одна сторона -> прямая вероятность из logprob (НЕ сигмоида):
        виден только PASS -> exp(lp_pass)
        виден только FAIL -> 1 - exp(lp_fail)
    Ни одной -> 0.5, prob_method='default'.
    """
    top = tok["top"] or {tok["token"]: tok["logprob"]}
    lp_pass, lp_fail = _side_logprob(top, "PASS"), _side_logprob(top, "FAIL")
    if lp_pass is None and lp_fail is None:
        return 0.5
    if lp_fail is None:
        return math.exp(lp_pass)
    if lp_pass is None:
        return 1.0 - math.exp(lp_fail)
    m = max(lp_pass, lp_fail)
    e_p, e_f = math.exp(lp_pass - m), math.exp(lp_fail - m)
    return e_p / (e_p + e_f)
```

### 2. Односимвольный подтокен

`logprobs.py:62` требует `len(s) >= 2` для префиксного матчинга, но `_verdict_positions` (`:29-43`) принимает односимвольное начало (`"P"`, `"F"`). Если токенизатор режет `PASS → "P" + "ASS"`, позиция находится, обе стороны дают `None`, результат — 0.5.

На OpenRouter не выстреливало; **на локальном vLLM токенизатор другой**. Снять ограничение `len(s) >= 2` для однобуквенных `P`/`F`, но сохранить приоритет точных совпадений над префиксными, чтобы префиксная масса не завышала сторону.

### 3. Позиции вердиктов

`logprobs.py:88-91` берёт первые два вхождения PASS/FAIL во всём потоке токенов. Промпт требует «сначала анализ, потом вердикты», поэтому любое упоминание PASS/FAIL в анализе сдвигает позиции.

Подтверждение: в `predictions/alfa_openrouter/m3/few_shot/test.jsonl` **42 из 223 строк** имеют `prob_method="logprobs"`, но вердиктов в хвосте `meta.raw` нет вообще.

Исправление: искать позиции **после** якоря `FAITHFULNESS:` / `RELEVANCE:` соответственно, а не в свободном потоке. Если якорь не найден — вернуть `None` и уйти в regex-фолбэк, а не брать случайные токены.

### 4. Regex-фолбэк

`parsing.py:9-12` требует `FAITHFULNESS:\s*(PASS|FAIL)`. Эволюционированные GEPA-промпты заставляют модель писать `- **FAITHFULNESS:** PASS` — проверено, **30 из 30 строк** `cloud/m3/gepa_plain_s0/{val,test}.jsonl` в таком формате.

Новый паттерн: `[-*\s]*\**\s*FAITHFULNESS\s*:?\**\s*(PASS|FAIL)`, регистронезависимо. Аналогично для RELEVANCE.

### 5. Обрыв генерации

`max_tokens=400` (`judge_client.py:210`) обрезает CoT до вердиктов. Поднять до 800 и добавить в `Prediction.meta` флаг `truncated: bool`, выставляемый когда `finish_reason == "length"`. Сейчас обрыв не фиксируется нигде.

### 6. Ключ кэша и содержимое

Текущий ключ (`judge_client.py:165-168`): `sha256(model ∥ system ∥ user)`. Добавить: `max_tokens`, `temperature`, `top_p`, `api_base`, `EXTRACTOR_VERSION` (константа модуля, инкрементируется при изменении логики извлечения).

**Критично:** кэш сейчас хранит выведенные `p_faith`/`p_rel` (`judge_client.py:186`). Переделать на хранение **сырых токенов с logprobs**. Иначе починка выше будет невидима на существующем кэше — прогон вернёт старые битые числа.

### 7. Обработка ошибок

`except RuntimeError` (`:205`, `:343`) при деградации logprobs — слишком узко: провайдер может ответить HTTP 400 на `logprobs=True`. Расширить до `except Exception` с логированием причины перехода на текстовый путь.
