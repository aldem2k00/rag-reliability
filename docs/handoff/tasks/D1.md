## Основание

Подтверждённые слепые зоны судьи — `chunk_fact_mixup` (27 маркеров) и `reason_missed_chunk_conditions` (9). Их не ловит ни один вариант.

Косвенная улика: при 8 чанках средний `p_faith` **выше**, чем при 5 (0.857 против 0.826 у zero-shot; 0.959 против 0.921 у few-shot). Больше дистракторов судья читает как «больше подтверждений» — направление неверное. Один холистический проход по 8 чанкам и ~5k токенов такие ошибки увидеть не может: модель ищет подтверждение, а не противоречие между источниками.

## Что сделать

### 1. Схема

```python
def score_per_chunk(sample, judge_fn, *, axis="faithfulness") -> dict[str, float]:
    """Для каждого чанка — отдельный вердикт судьи по оси faithfulness.

    для i в 1..n_chunks:
        s_i = judge_fn(вопрос, диалог, ТОЛЬКО чанк_i, ответ)

    scores:
      m3.max_chunk_score      max_i s_i        есть ли хоть один источник опоры
      m3.mean_chunk_score     mean_i s_i
      m3.chunk_disagreement   top1(s) - top2(s)   ЦЕЛЕВАЯ ФИЧА
      m3.n_supporting         |{i : s_i > theta}|
      m3.argmax_chunk         индекс лучшего источника
    """
```

**`m3.chunk_disagreement` — целевая фича.** Если два чанка дают высокие, но несовместимые скоры, это подпись смешения фактов из разных источников.

### 2. Предупреждение из литературы — соблюсти обязательно

Декомпозиция помогает **только при выровненном evidence**: когда проверяемая единица сопоставляется с гранулярно соответствующим ей источником. При невыровненном evidence эффект отрицательный (−0.067 F1 на одном из бенчмарков).

Практический вывод: декомпозировать **по чанкам** (каждый чанк — отдельный источник), а **не** «каждое утверждение против склейки всех восьми». Второй вариант — ровно тот антипаттерн, от которого предостерегает литература. Не реализовывать его даже как опцию.

### 3. Стоимость

Наивно ×8 вызовов, но каждый промпт короче: один чанк ~400 токенов вместо ~2000. Суммарный prompt-объём сопоставим с холистическим проходом; с prefix caching в vLLM (общая часть — вопрос, диалог, ответ) — заметно меньше. Оценка: **~40 мин на полный корпус** на A100.

Реализовать батчинг: все 8 запросов одного кейса уходят одним пакетом через `chat(n=...)`-подобный механизм или асинхронный клиент с семафором (`AsyncJudgeClient` уже есть).

### 4. Только ось faithfulness

Relevance не зависит от чанков — оси разделены в C3, и промпт relevance чанки не получает вовсе. Per-chunk применяется только к faithfulness.

## Тесты

На dummy-бэкенде.

- при `n_chunks = 5` делается ровно 5 вызовов, при 8 — ровно 8;
- `chunk_disagreement` = 0 при одинаковых скорах, максимален при двух высоких и остальных низких;
- `argmax_chunk` соответствует максимуму;
- в промпт для чанка `i` попадает **только** чанк `i` (проверить по тексту запроса);
- кейс с одним чанком не падает (`top2` не существует — вернуть 0);
- вызовы батчатся: мок-клиент фиксирует число сетевых обращений.
