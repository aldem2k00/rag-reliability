## Проблема

Каждый метод пишет `val.jsonl` и `test.jsonl` — предсказания физически привязаны к разбиению. Отсюда четыре несовместимых протокола сплита в одной кодовой базе и невозможность сменить сплит без перепрогона всех методов.

Целевой принцип: **метод производит скоры по всему корпусу; сплит применяется на этапе оценки.**

## Что сделать

### 1. `scripts/score.py`

```bash
python scripts/score.py --method m3_judge --variant zero_shot \
    --data data/organizers.jsonl \
    --output predictions/m3_judge/zero_shot/scores.jsonl \
    [--limit N] [--resume] [прочие опции метода]
```

Поведение:

- прогоняет метод по **всему** файлу данных, не по сплиту;
- пишет `scores.jsonl` — по одной строке `Prediction` на кейс, с заполненным `scores`;
- рядом кладёт `run.yaml` (конфиг + `git_state()` + seed + версия метода);
- `--resume` продолжает прерванный прогон: читает уже записанные id и досчитывает остальные. Это обязательно — прогоны на DataSphere прерываются;
- пишет **инкрементально** (flush после каждых N строк), а не в конце;
- `--limit N` — для смоуков, при этом в `run.yaml` пишется `partial: true`.

### 2. Скоры вместо бинарных решений

**Ключевое требование.** Метод больше не бинаризует. `faithfulness_pred`/`relevance_pred` заполняются нулями и переопределяются протоколом (B1). Метод обязан заполнить `scores` и, где применимо, `faithfulness_prob`/`relevance_prob`.

Это устраняет класс ошибок, где «жёсткое» решение метода конфликтует с подобранным порогом. Сейчас `run_m3.py:50-51` бинаризует по 0.5, а отчёты используют пороги 0.30/0.63 — то есть бинарные поля в артефактах не соответствуют опубликованным числам.

Исключение: `independent` (rule-based) по природе бинарен — он заполняет и `_pred`, и `scores` с производным непрерывным сигналом.

### 3. Переработка реестра

`MethodSpec` дополняется:

```python
@dataclass(frozen=True)
class MethodSpec:
    name: str
    label: str
    family: str
    mode: str | None
    build_command: BuildCommand
    demo_runner: str | None
    requires: tuple[str, ...] = ()
    # NEW
    score_keys: tuple[str, ...] = ()      # какие ключи scores метод обязан заполнить
    default_score_expr: str | None = None # выражение по умолчанию для evaluate_cv
    corpus_wide: bool = True              # умеет ли скорить весь корпус за прогон
```

`score_keys` — контракт: `score.py` после прогона **проверяет**, что все заявленные ключи присутствуют во всех строках, и падает с понятной ошибкой, если нет. Это ловит молчаливую деградацию метода.

Заполнить для существующих методов:

| Метод | `score_keys` | `default_score_expr` |
|---|---|---|
| `surface` | `surf.p_faith`, `surf.p_rel` | `surf.p_faith * surf.p_rel` |
| `m3_openai_judge` | `m3.p_faith`, `m3.p_rel` | `m3.p_faith * m3.p_rel` |
| `lettucedetect` | `ld.max_unsup`, `ld.mean_unsup`, `ld.frac_unsup` | `1 - ld.max_unsup` |
| `encoder` | `enc.logit` | `enc.logit` |
| `independent` | `ind.faith_score`, `ind.rel_score` | `ind.faith_score * ind.rel_score` |
| `majority` | `surf.p_faith`, `surf.p_rel` (константы) | — |

### 4. Валидация артефакта

```python
def validate_scores_file(path, spec, expected_n=None) -> None:
    """Проверяет: нет дублей id, все score_keys присутствуют в каждой строке,
    значения конечны, при expected_n — совпадает количество.

    Отсутствие ключа — ошибка. Никаких .get(key, default): в M6 молчаливый
    дефолт привёл к тому, что битая строка признаков трактовалась как
    идеально надёжный кейс.
    """
```

Вызывается автоматически в конце `score.py`.

### 5. Обратная совместимость демо и бенчмарка

`rag-judge` CLI (`cli.py`), `run_benchmark.py` и Gradio-демо читают реестр. Они не должны сломаться. Если `MethodSpec` меняется — обнови их вызовы **минимально**, без изменения поведения, и укажи это в PR (это разрешённое исключение из правила владения, потому что реестр — твой).
