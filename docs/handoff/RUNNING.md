# RUNNING — как запускать: сессии и промпты

Операционный документ. Отвечает на два вопроса: сколько сессий заводить и что в них писать.

---

## 1. Правило: одна сессия — одна задача

Не одна длинная сессия на всё. Причины по убыванию важности:

1. **Волны параллельны по построению.** Пять задач первой волны — это пять одновременных
   сессий, иначе весь смысл матрицы владения теряется.
2. **Изоляция контекста.** Карточка занимает 8–10 КБ, плюс файлы, которые агент читает.
   Сессия, ведущая три задачи подряд, к третьей уже вытеснила детали первой — а вытесняются
   именно точные требования, не общие.
3. **Изоляция ошибок.** Задача пошла не туда — выбрасывается одна сессия, а не весь контекст.
4. **Загрязнение решений.** Агент, только что правивший `m6/predict.py`, при переходе к
   `stacking/` тащит за собой сделанные там компромиссы. Это тихий эффект, его не видно в диффе.

Исключение — мелкие механические задачи одной волны (A3 и A5) можно вести в одной сессии
последовательно, если очень хочется. Всё остальное — раздельно.

## 2. Карта сессий на волну

На примере волны 1 (5 задач):

| Сессия | Кто | Что делает | Длительность |
|---|---|---|---|
| impl × 5 | Codex (A2–A5) / Claude Code (A1) | реализация по карточке | от 20 мин до 2 ч |
| verify × 5 | **другое семейство**, чем импл | проверка критериев по диффу | 10–20 мин |
| integrator × 1 | Claude Code | мерж PR, `make check`, решение о переходе к волне 2 | 20 мин |

Итого ~11 сессий на волну, ~40 на весь роадмап. Большинство короткие.

Верификацию мелких задач (A3, A5) можно объединить в одну сессию — но только их,
и только если обе от одного исполнителя.

## 3. Промпты

Главный принцип: **промпт короткий, карточка длинная.** Не пересказывай спецификацию в
промпте — агент смешает пересказ с оригиналом и уедет в сторону. Задача промпта: указать
на карточку, поставить границы, определить «готово».

### 3.1 Реализация

```
Прочитай AGENTS.md и docs/handoff/tasks/A1.md.

Выполни задачу A1 целиком. Меняй только файлы из раздела «Владеет» — всё
остальное read-only. Коммить после каждого логического шага.

Когда закончишь: прогони критерии приёмки по одному, каждый с командой проверки,
и открой PR в ветку integration. В описании PR — числа, которые требует раздел
«В PR обязательно указать».
```

Всё. Ни слова о проекте, метриках или архитектуре — это в `AGENTS.md`.

Для задач с планированием (A1, B1, C2, C4, осторожно B2) добавить первой строкой:

```
Сначала составь план реализации КАРТОЧКИ (не пересматривая её решения), покажи мне,
дождись подтверждения. Потом реализуй.
```

### 3.2 Верификация

Запускать **в другом семействе**, чем реализация, и в чистой сессии.

```
Прочитай docs/handoff/tasks/A1.md и посмотри дифф ветки task/A1-splits
относительно integration.

Проверь КАЖДЫЙ критерий приёмки отдельно, запуская команды проверки.

Отдельно ответь на вопрос: не закрепляет ли какой-нибудь новый тест неверное
поведение? Прецедент — tests/test_m3_logprobs.py:66-69, где тест требовал, чтобы
токен с P(PASS)=0.905 давал 0.475; тест был зелёный, и баг прожил три ветки.

Верни таблицу: критерий → выполнен/нет → доказательство (вывод команды).
Ничего не исправляй и не коммить.
```

Последняя строка обязательна: верификатор, который начинает чинить, перестаёт быть
независимым.

### 3.3 Интегратор (одна сессия на волну)

```
Волна 1 закончена, PR-ы task/A1-splits, task/A2-stats, task/A3-schema,
task/A4-logprobs, task/A5-hygiene открыты в integration.

1. Влей их в порядке: A3, A2, A1, A4, A5. После каждого мержа — make check.
2. Если конфликт — не решай творчески: посмотри матрицу владения в
   HANDOFF.md §6 и определи, кто вышел за свои файлы. Это баг задачи, а не мержа.
3. Прогони критерии выхода из фазы 0 (docs/specs/10_PHASE0 §7).
4. Выпиши в docs/report/wave1.md: какие числа получены, какие критерии не закрыты,
   что блокирует волну 2.
```

Порядок мержа не случаен: A3 фиксирует `Prediction.scores`, от которого зависят остальные.

### 3.4 Сессия закончилась, задача — нет

Большие задачи (A1, B1, C2, C4) могут не влезть. Восстановление:

```
Продолжаю задачу A1 после обрыва сессии.

Прочитай AGENTS.md, docs/handoff/tasks/A1.md, затем git log и git diff в этом
worktree — там уже сделанная часть.

Определи, какие пункты «Что сделать» уже закрыты, и продолжи с первого незакрытого.
Ничего из сделанного не переписывай без причины.
```

Работает только если предыдущая сессия коммитила по ходу. Отсюда требование
«коммить после каждого логического шага» в промпте реализации — оно операционное,
а не стилистическое.

### 3.5 Задача пошла не туда

Признаки: агент правит файлы вне «Владеет», переспорил решение карточки, третий раз
переписывает один модуль.

Не уговаривай — выбрось сессию:

```
git worktree remove --force ../wt-A1 && git branch -D task/A1-splits
git worktree add ../wt-A1 -b task/A1-splits integration
```

И запусти заново, добавив в промпт одну строку про то, что именно пошло не так:
«В прошлый раз агент пересмотрел решение про один порог — оно зафиксировано в
карточке, не меняй его».

## 4. Роль «штабной» сессии

Отдельно от исполнения полезна одна долгая сессия (Cowork или Claude Code), которая
держит контекст аудита: числа, диагнозы, обоснования решений. К ней ходят, когда:

- карточка противоречит тому, что агент нашёл в коде;
- получено число, и непонятно, хорошее оно или внутри шума;
- надо решить, стоит ли отклоняться от плана.

Эта сессия ничего не реализует. Её ценность — в том, что она помнит, почему приняты
решения, а исполнительные сессии этого не знают и знать не должны.

## 5. Антипаттерны

| Не делай | Что произойдёт |
|---|---|
| Одна сессия на всю волну | к третьей задаче вытеснятся точные требования первой |
| Продолжать в той же сессии после мержа PR | агент тащит решения прошлой задачи в новую |
| Пересказывать проект в промпте | пересказ смешается с `AGENTS.md`, агент уедет в сторону |
| Верифицировать в сессии, где реализовывал | разделяются слепые пятна; проверка становится ритуалом |
| Верифицировать тем же семейством | то же, слабее |
| Уговаривать сбившегося агента | дешевле пересоздать worktree |
| Читать дифф вместо PR-описания | для механических задач хватит описания; читать надо числа |

## 6. Что читать человеку

Не весь дифф. По задачам:

| Задача | Что смотреть глазами |
|---|---|
| A1 | числа `leak_check`, размер крупнейшей группы, сколько кейсов исключено |
| A2 | таблицу пяти прогонов с ДИ и перцентилями шума |
| A4 | сколько расхождений осталось из 64 (ожидание — 0) |
| B1 | воспроизвелись ли 10 старых чисел до 1e-6 |
| C1 | абляционную таблицу и финальный набор фич |
| C4 | ROC-AUC grounding с ДИ — от него зависит судьба ветки |
| остальные | PR-описание и вывод верификатора |
