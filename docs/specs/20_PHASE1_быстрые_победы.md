## 1. Задача 1.1 — стэкинг разнородных сигналов

**Ожидаемый эффект: +0.03…+0.06 macro-F1. Стоимость: 1 день, 0 GPU.**

### 1.1 Основание

Измерено на уже закоммиченных артефактах, 5×5-fold CV на 446 размеченных кейсах:

| Набор сигналов | ROC-AUC | macro-F1 |
|---|---:|---:|
| только surface (2 фичи) | 0.6218 ± 0.0021 | 0.5798 ± 0.0035 |
| только M3 zero-shot (2 фичи) | 0.5657 ± 0.0044 | 0.5794 ± 0.0035 |
| **surface + `m3.p_faith`** | **0.6277 ± 0.0035** | **0.6085 ± 0.0066** |
| surface + обе оси судьи | 0.6276 ± 0.0027 | 0.6077 ± 0.0060 |
| все 8 сигналов | 0.6199 ± 0.0033 | 0.6160 ± 0.0117 |

Честный вариант (обучение на val, применение к test): **0.6205** против лучшего опубликованного 0.5982.

Два вывода, определяющих дизайн:

- **`m3.p_rel` не добавляет ничего** (0.6085 → 0.6077). Его AUC = 0.497. В стэк не включать.
- **На 8 фичах AUC падает** (0.6277 → 0.6199) при росте F1 — переобучение. Литература по калибровке панелей судей при конечном бюджете меток прямо рекомендует **скалярную агрегацию, а не joint-table**: скалярная выигрывает в 16 из 20 ячеек «датасет × бюджет». Держать 5–7 фич.

## 2. Задача 1.2 — починка извлечения вероятностей

**Ожидаемый эффект: на текущих числах малый; блокирующий для переезда на vLLM. Стоимость: 0.5 дня.**

### 2.1 Баг

`src/rag_reliability/methods/m3/logprobs.py:77-80`:

```python
if lp_pass is None:
    return 1.0 - 1.0 / (1.0 + math.exp(-lp_fail))
if lp_fail is None:
    return 1.0 / (1.0 + math.exp(-lp_pass))
```

`lp` — логарифм вероятности, всегда ≤ 0 ⟹ `sigmoid(lp) ∈ (0, 0.5]`. Монотонность инвертирована в зоне уверенности:

| P(PASS) | logprob | текущий результат | верный |
|---:|---:|---:|---:|
| 0.999 | −0.0010 | 0.4997 | 0.999 |
| 0.9 | −0.1054 | 0.4737 | 0.9 |
| 0.1 | −2.3026 | 0.0909 | 0.1 |

Подтверждено на артефактах: 64 расхождения «записанное `p`» vs «текстовый вердикт», из них 61 со значением `p ∈ [0.49, 0.51]`. Худший файл — `gepa_plain_s1/val.jsonl`: 11 расхождений из 28.

### 2.2 Исправление

```python
def _pass_prob(tok: Token) -> float:
    """P(PASS) в позиции вердикта.

    Обе стороны видны -> softmax по паре.
    Видна одна сторона -> прямая вероятность из logprob (НЕ сигмоида):
        p_pass = exp(lp_pass)          если виден только PASS
        p_pass = 1 - exp(lp_fail)      если виден только FAIL
    Ни одной -> 0.5 и prob_method='default'.
    """
    top = tok["top"] or {tok["token"]: tok["logprob"]}
    lp_pass, lp_fail = _side_logprob(top, "PASS"), _side_logprob(top, "FAIL")
    if lp_pass is None and lp_fail is None:
        return 0.5
    if lp_fail is None:
        return math.exp(lp_pass)
    if lp_pass is None:
        return 1.0 - math.exp(lp_fail)
    m = max(lp_pass, lp_fail)
    e_p, e_f = math.exp(lp_pass - m), math.exp(lp_fail - m)
    return e_p / (e_p + e_f)
```

## 3. Задача 1.3 — энкодер на полном контексте

**Ожидаемый эффект: вероятно крупнейший единичный прирост. Стоимость: 1 день + ~4 GPU-ч.**

### 3.1 Основание

`deepvk/RuModernBERT-base` имеет `max_position_embeddings = 8192` (проверено по `config.json`). Обучение идёт при `--max-length 512` (`train_encoder_baseline.py:42`) при медианном контексте 6371 символ (~2000–2500 токенов) и p95 12745 символов. **Модель видит меньше четверти входа.**

Вывод в `docs/experiments.md` «Longer context at 1024 hurts macro-F1 because the model becomes too positive» построен на прогоне, который **выродился**: recall = 1.0000, macro-F1 = 0.4191, то есть класс схлопнулся. Это провал обучения, а не свойство длины. Вывод снимается.

### 3.2 План эксперимента

Сетка (5-fold OOF, без повторов — см. `10_PHASE0` §6):

| Ось | Значения |
|---|---|
| `max_length` | 512 (контроль), 2048, 4096, 8192 |
| LR | 2e-5, 1e-5 (для длинного контекста ниже) |
| warmup_ratio | 0.06 (сейчас, судя по коду, отсутствует — добавить) |
| batch / grad_accum | подобрать под VRAM: 8192 × bs1 × accum8 на A100 80GB |
| class weighting | none, `pos_weight = n_neg/n_pos` |

**Обязательный контроль схлопывания.** После каждой эпохи логировать `degenerate_rate` (доля самого частого предсказания). Прогон, где `const_share > 0.98`, помечается `collapsed: true` и **не участвует** в выборе лучшей конфигурации. Прошлый вывод про 1024 был сделан именно на таком прогоне.

### 3.4 Альтернатива, если 8192 не помогает

Если разница 512 → 8192 внутри ДИ, проверить две гипотезы, прежде чем отказываться:

1. **Позиционный bias (lost-in-the-middle).** Перемешать порядок чанков и посмотреть на дисперсию предсказания. Это единственная непроверенная гипотеза из аудита.
2. **Per-chunk агрегация вместо склейки.** 8 независимых проходов (диалог + вопрос + чанк_i + ответ) при 1024 токенах, агрегация max/attention. Дешевле по памяти, чем 8192, и даёт per-chunk атрибуцию — тот же механизм, что в задаче 2.4.

## 4. Задача 1.4 — прогон судьи по всему корпусу

**Стоимость: ~15 мин на A100 + 0.5 дня на анализ.**

### 4.1 Зачем

В объединённом пуле val+test (446 кейсов) всего **33 маркер-инстанса**, крупнейший класс — 6 экземпляров. Любые утверждения вида «GEPA не ловит `chunk_fact_mixup`» на этих сплитах статистической основы не имеют. На полном корпусе — 200 маркер-упоминаний, 158 размеченных кейсов.

### 4.2 Расчёт стоимости

| Величина | Значение |
|---|---|
| Кейсов | 2233 |
| Prompt-токенов на кейс | ~3000 (контекст p50 ≈ 2000 + диалог + шаблон) |
| Output-токенов на кейс | ~300 |
| Итого prompt | ~6.7 M |
| Итого output | ~0.7 M |
| Prefill на A100 (Qwen2.5-7B, vLLM) | ~15k tok/s → ~7.5 мин |
| Decode | ~2k tok/s → ~6 мин |
| **Полный проход** | **~15 мин** |

Этап на OpenRouter выглядел дорогим; локально он практически бесплатен. Это меняет экономику всей фазы 2.

### 4.3 Что построить на выходе

`scripts/analyze_markers.py`:

- per-marker recall при рабочем пороге, с ДИ Уилсона (классы малые);
- AUC сигнала для каждой маркерной подгруппы против всех reliable-кейсов;
- явное указание n для каждого класса; классы с n < 10 помечаются `underpowered: true` и не участвуют в выводах;
- отдельная строка для 483 негативов **без** маркера (77.5% всех негативов) — на них диагностика по типам ошибок невозможна в принципе, и это надо сказать.

## 5. Задача 1.5 — порог по вероятности вместо argmax

**Стоимость: 2 часа.**

`scripts/run_m3.py:50-51` бинаризует жёстко по 0.5; `thresholds.py` на текущей ветке это чинит, но результат не доведён до `main` и до отчётов. После фазы 0 порог живёт в `evaluation/protocol.py` и подбирается на train-фолдах — задача сводится к тому, чтобы **инференс перестал бинаризовать вообще** и писал только скоры.

Правило: `run_m3.py` и любой другой скоринг пишет `scores`, `faithfulness_prob`, `relevance_prob`; поля `faithfulness_pred`/`relevance_pred` заполняются нулями и переопределяются протоколом. Это устраняет класс ошибок, где «жёсткое» решение метода конфликтует с подобранным порогом.
