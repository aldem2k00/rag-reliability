## 1. Задача 2.1 — разделить оси и переписать промпт relevance

**Ожидаемый эффект: высокий. Это самый большой резерв метода.**

### 1.1 Почему одна ось мертва

Промпт (`m3/prompts.py:15-29`) формулирует relevance как «ответ соответствует вопросу». Определение организаторов существенно жёстче — rel = 0, если ответ:

- не адресует вопрос клиента;
- **отвечает на другой, хотя и смежный вопрос**;
- **содержит информацию, предназначенную оператору**;
- **содержит уточняющий вопрос вместо ответа**;
- **перенаправляет в статью вместо ответа**.

Ни один из четырёх выделенных критериев в промпте не упомянут. При этом `reason_answer_for_operator` — второй по частоте маркер (27 из 200).

Вторая причина — интерференция осей в одном вызове. Прямая улика в артефактах (`gepa_plain_s0/val.jsonl`, `pseudo_00059`): `**FAITHFULNESS:** Ответ не добавляет новых фактов, но не полностью отвечает на вопрос клиента` — аргумент про relevance внутри вердикта по faithfulness.

### 1.2 Новая структура промптов

Два независимых вызова вместо одного. Модуль `m3/prompts.py` расширяется:

```python
AXIS_FAITHFULNESS = "faithfulness"
AXIS_RELEVANCE = "relevance"

def build_axis_prompt(sample, axis: str, *, mode: str, examples=None) -> tuple[str, str]:
    """(system, user) для одной оси. Оси не видят критериев друг друга."""
```

**Промпт relevance — обязательные элементы** (по определению организаторов, дословно, а не пересказом):

```
Ты проверяешь, отвечает ли ответ бота на вопрос клиента.

Поставь FAIL, если выполнено хотя бы одно:
  1. Ответ не адресует вопрос клиента.
  2. Ответ отвечает на другой, пусть и смежный, вопрос.
  3. Ответ содержит информацию, предназначенную оператору, а не клиенту
     (инструкции по обработке обращения, служебные пометки, «сообщите клиенту…»).
  4. Ответ содержит уточняющий вопрос вместо ответа.
  5. Ответ перенаправляет клиента в статью или на страницу вместо того,
     чтобы ответить.
  6. Ответ покрывает не все части вопроса, если вопрос состоял из нескольких.

Поставь PASS, если ответ по существу решает проблему клиента, даже если он
неполон в деталях (неполнота по фактам — это ось faithfulness, не твоя).

Учитывай историю диалога: вопрос может быть уточнением предыдущего.
```

Последний абзац критичен: разметка организаторов ставит `1` даже неполному ответу, если он релевантен (их пример 1 — «На 62 дня — 19.84%»). Без этого судья будет штрафовать неполноту дважды.

**Промпт faithfulness — что добавить** к текущему:

```
  7. Ответ использует нерелевантный чанк (reason_irrelevant_chunk_used).
  8. Ответ утверждает, что что-то проверил или вычислил, хотя этого не было
     (reason_false_verification).
  9. Ответ использует устаревшую информацию, если в чанках есть актуальная.
 10. Ответ раскрывает, что он сгенерирован ИИ.
 11. Ответ ведёт по неверной ссылке/разделу относительно чанков.
```

Сейчас промпт покрывает ~6 из 13 маркеров таксономии. `configs/markers.yaml` подключён только к feedback GEPA (`gepa.py:66-69`) и никогда — к инференсу.

### 1.3 Стоимость

Два вызова вместо одного: ~30 мин на полный корпус вместо 15. При этом промпт relevance короче (ему не нужны все 8 чанков — достаточно вопроса, диалога и ответа), так что реальная стоимость ниже двукратной.

**Важный побочный эффект:** промпт relevance без контекста — это ~600 prompt-токенов вместо ~3000. Полный проход по relevance стоит ~3 минуты.

### 1.4 Критерии приёмки

- [ ] AUC(`p_rel`, relevance) ≥ 0.60 на OOF по 2233 (сейчас 0.497)
- [ ] доля `RELEVANCE: PASS` ≤ 92% (сейчас 98.6–100% при золоте 84.9%)
- [ ] recall на подгруппе `reason_answer_for_operator` измерен и указан с ДИ Уилсона
- [ ] `m3.p_rel` проходит проверку на включение в стэк (нижняя граница ДИ приращения > 0)

## 2. Задача 2.2 — self-consistency

**Ожидаемый эффект: высокий. Стоимость: ~2 GPU-ч.**

### 2.1 Почему это нужно

`p_faith > 0.99` у 50–79% кейсов. Такая масса связок физически ограничивает AUC: ранжировать нечего. Голосование по N сэмплам даёт настоящую гранулярность ранга при том же промпте и той же модели.

Литература: усреднение по k=8 даёт +9.8 п.п. точности при 1.3× стоимости, причём малые модели выигрывают непропорционально — mini+criteria при k=8 сравнивается с полной моделью при четверти стоимости.

### 2.2 Реализация

Инфраструктура **уже есть и не используется**: `judge_client.chat(n=...)` (`judge_client.py:121-162`) поддерживает `n>1` с деградацией в последовательные вызовы, но `judge()` его не пробрасывает, а `T=0` захардкожен (`:204`, `:342`).

```python
def judge_selfconsistent(
    self, system: str, user: str, *, n: int = 8, temperature: float = 0.7
) -> JudgeVerdict:
    """N сэмплов -> усреднение вероятностей + доля PASS-голосов.

    Возвращает scores:
      m3.p_faith          среднее по сэмплам (усреднять вероятности, не голоса)
      m3.p_faith_vote     доля сэмплов с PASS
      m3.p_faith_std      разброс — сам по себе сигнал неуверенности
    """
```

**Усреднять вероятности, а не голоса.** Голоса дают гранулярность 1/N; усреднение вероятностей сохраняет непрерывность. Держать оба: `p_faith_vote` может оказаться устойчивее при насыщенных logprobs.

`p_faith_std` — самостоятельная фича для стэка: разброс судьи по сэмплам коррелирует с трудностью кейса.

### 2.3 Сетка

| Параметр | Значения для абляции |
|---|---|
| N | 1 (контроль), 4, 8, 16 |
| T | 0.7, 1.0 |
| агрегация | mean-prob, vote-share, median |

Обязательно построить **кривую качество/цена по N** — эта таблица требуется контрактом платформы и не была построена ни разу.

### 2.4 Критерии приёмки

- [ ] доля `p_faith > 0.99` падает ниже 30%
- [ ] AUC(`p_faith`, faithfulness) растёт; прирост подтверждён ДИ
- [ ] таблица качество/цена по N ∈ {1,4,8,16} в `report.json`
- [ ] `m3.p_faith_std` проверена как отдельная фича стэка

## 3. Задача 2.3 — criteria injection

**Ожидаемый эффект: средний. Стоимость: почти нулевая.**

`configs/markers.yaml` содержит глоссы всех 13 маркеров и используется только в feedback GEPA. Превратить их в чеклист внутри промпта:

```
Проверь по списку. Если сработал хотя бы один пункт — FAIL, и назови его код.
[список 13 однострочных критериев из markers.yaml]

Формат ответа:
ANALYSIS: <краткий разбор>
MARKER: <код или none>
FAITHFULNESS: PASS|FAIL
RELEVANCE: PASS|FAIL
```

Три эффекта сразу:

1. **Качество.** По литературе criteria injection даёт +3.0 п.п. бесплатно, а совместно с self-consistency k=8 — +13.5 п.п.
2. **Интерпретируемость.** `marker_pred` заполняется, появляется вход в per-marker recall.
3. **Диагностика.** Распределение предсказанных маркеров показывает, какие типы ошибок судья вообще способен различать.

**Внимание к формату вывода.** Добавление `MARKER:` перед вердиктами сдвигает позиции токенов PASS/FAIL — это ровно баг Б5 (`logprobs.py:88-91` берёт первые два вхождения в потоке). Задача 1.2(б) должна быть закрыта **до** этой.

## 4. Задача 2.4 — пофрагментная верификация

**Ожидаемый эффект: высокий на конкретных типах ошибок. Стоимость: ~4 GPU-ч.**

### 4.1 Основание

Подтверждённые слепые зоны — `chunk_fact_mixup` (27 маркеров) и `reason_missed_chunk_conditions` (9). Их не ловит ни один вариант судьи. Косвенная улика: при 8 чанках средний `p_faith` **выше**, чем при 5 (0.857 против 0.826) — больше дистракторов судья читает как «больше подтверждений».

Один холистический проход по 8 чанкам и ~5k токенов такие ошибки увидеть не может: модель ищет подтверждение, а не противоречие между источниками.

### 4.2 Схема

```
для каждого чанка i ∈ 1..n_chunks:
    judge(вопрос, диалог, ТОЛЬКО чанк_i, ответ) -> s_i ∈ [0,1]

scores:
  m3.max_chunk_score        max_i s_i          — есть ли хоть один источник опоры
  m3.mean_chunk_score       mean_i s_i
  m3.chunk_disagreement     top1(s) - top2(s)  — детектор cross-chunk mixup
  m3.n_supporting           |{i : s_i > θ}|
```

**`chunk_disagreement` — целевая фича.** Если два чанка дают высокие, но несовместимые скоры, это подпись смешения фактов из разных источников.

### 4.3 Важное предупреждение из литературы

Декомпозиция помогает **только при выровненном evidence**: когда sub-claim проверяется против гранулярно соответствующего ему источника. При подстановке повторённого claim-level evidence эффект нейтрален или вреден (−0.067 F1 на одном из бенчмарков).

Практический вывод: декомпозировать **по чанкам** (каждый чанк — отдельный источник), а не «каждое утверждение против склейки всех восьми». Второй вариант — именно тот антипаттерн, от которого предостерегает литература.

### 4.4 Стоимость

Наивно ×8 вызовов. Но каждый промпт короче: один чанк ~400 токенов вместо ~2000. Суммарный prompt-объём сопоставим с одним холистическим проходом; с prefix caching в vLLM (общая часть — вопрос, диалог, ответ) — заметно меньше. Оценка: ~40 мин на полный корпус.

### 4.5 Критерии приёмки

- [ ] recall на подгруппе `reason_chunk_fact_mixup` вырос относительно холистического судьи (с ДИ)
- [ ] `m3.chunk_disagreement` проверена как фича стэка
- [ ] эффект «больше чанков → выше `p_faith`» исчез или ослаб

### 5.2 Метрика для GEPA

При базовой ставке reliable 72% точность почти плоская: кандидат может улучшить accuracy, чаще отвечая PASS, и **ухудшить** macro-F1. Это и наблюдалось — все кандидаты в 0.617–0.733.

```python
def gepa_metric(example, prediction, trace=None) -> float:
    """Balanced accuracy по двум осям — устойчива к дисбалансу 72/28
    и не требует подбора порога внутри цикла оптимизации."""
    return 0.5 * (
        recall_pos(example.faith, prediction.faith) +
        recall_neg(example.faith, prediction.faith)
    ) * 0.5 + ...
```

### 5.3 Feedback с диагностикой

```python
def gepa_feedback(example, prediction, *, use_markers: bool) -> str:
    if correct: return "Верно."
    parts = [f"Ошибка. Правильный ответ: FAITHFULNESS={...}, RELEVANCE={...}."]
    if use_markers and example.marker:
        parts.append(f"Тип ошибки: {MARKER_GLOSS[example.marker]}.")
        parts.append(f"Признак в ответе: {example.marker_evidence}.")   # NEW
    parts.append(f"Ответ содержал: «{snippet(example.answer)}»; "
                 f"в чанках это не подтверждается / противоречит чанку {i}.")  # NEW
    return " ".join(parts)
```

Без последних двух строк рефлексирующая LM узнаёт *что*, но не *почему* — именно поэтому эволюция и упёрлась в 2 решения из 60.

### 5.4 Протокол H5

| Вариант | Сидов | Данные | Бюджет |
|---|---|---|---|
| markers | 3 (0,1,2) | реальный корпус, D_pareto = 300 | `auto=medium` |
| plain | 3 (0,1,2) | те же 300 | тот же |

Сравнение — парный бутстрэп по сидам и по кейсам. Стоп-правило: **отвергаем H5, если верхняя граница 95% ДИ приращения (markers − plain) < 0**. Не «если точечная оценка ниже».

Отдельно: перед запуском на реальных данных убедиться, что промпты не наследуют содержимое псевдо-корпуса. В текущих эволюционированных инструкциях вшиты примеры про телескоп «Хаббл», соул-джаз и Парфенон, а в одном — контекст `[Чанк 2] (...)`, то есть судью учат, что чанки бывают пустыми.

## 6. Задача 2.6 — обучаемый судья (H1 по существу)

**Ожидаемый эффект: потенциально высокий. Стоимость: ~8 GPU-ч.**

### 6.1 Что уже есть

`notebooks/qwen7b_full_finetune_datasphere.ipynb` — полный FT Qwen2.5-7B на A100 80GB, 8-bit AdamW, gradient checkpointing, bf16.

**Два блокера, которые надо снять до запуска:**

1. Ячейка [4]: `train, val, test_samples = split_samples(samples, seed=SEED)` — это протокол A, тот самый протекающий. Заменить на чтение `folds.json`.
2. Ячейка [2] клонирует ветку `qwen7b-notebook` — устарела относительно рабочей.

### 6.2 Гиперпараметры

Прошлый LoRA-прогон на 1.5B схлопнулся в (1,1) при несбалансированной выборке и не побил zero-shot даже после балансировки. Причины и что менять:

| Что | Было | Стало | Обоснование |
|---|---|---|---|
| Модель | Qwen2.5-1.5B-4bit | Qwen2.5-7B / Qwen3-4B | 1.5B в 4-битах слишком слаба для тонких ошибок |
| LoRA target | attention | **все линейные, включая MLP** | паритет с full FT достигается только так |
| rank / alpha | низкий | **r=256, α=512** | тот же источник |
| LR | как для full FT | **×10 (≈2e-4)** | оптимальный LR для LoRA примерно на порядок выше |
| Баланс классов | несбалансированно / 256×4 | взвешенный лосс + oversampling негативов | схлопывание было следствием дисбаланса |
| Выход | генеративный вердикт | генеративный вердикт **+ logprob** | logprob нужен стэку |

### 6.3 Full FT vs LoRA

Прогнать оба и сравнить с ДИ. Full FT 7B на A100 80GB с 8-bit AdamW помещается (ноутбук это уже проверяет ассертом на 70 GB VRAM). LoRA дешевле и позволяет 5-fold OOF; full FT — 5 обучений по ~1.5 ч.

**Компромисс по OOF:** обучать 5 фолдов без повторов, разброс оценивать бутстрэпом по кейсам. Записать в `report.json` как `n_repeats: 1`.

- [ ] обучение читает `folds.json`, а не пересплитывает
- [ ] `degenerate.const_share < 0.9` на всех фолдах (контроль схлопывания)
- [ ] H1 закрыта числом с ДИ: fine-tuned vs prompt-optimized при одинаковом backbone
- [ ] `scores.jsonl` с logprob-вероятностями закоммичен

## 7. Задача 2.7 — kNN-augmented judging (опционально)

**Ожидаемый эффект: средний. Стоимость: 0.5 дня + эмбеддинги.**

Вместо фиксированных few-shot-примеров подставлять 5 ближайших размеченных кейсов из train-фолдов (эмбеддинги `deepvk/USER2-base`, 8192 контекста).

Обоснование: 1-NN на group-aware сплите даёт 0.5125 — то есть в корпусе есть локальная структура, которую судья сейчас не использует. Как предсказание она слаба, но как контекст для судьи может работать лучше.

**Строгое требование:** соседи берутся **только из train-фолдов** текущего фолда. Иначе это утечка, и она будет выглядеть как большой прирост.
