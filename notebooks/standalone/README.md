# Самостоятельные ноутбуки методов 3 и 6

Два ноутбука, каждый — разбор своего метода целиком: постановка, гипотезы, код метода,
прогон, метрики, вердикт. Их можно открыть и прочитать, не заглядывая в репозиторий, —
по образцу [`from_organizators/baseline.ipynb`](../../from_organizators/baseline.ipynb).

| Ноутбук | Метод | Что проверяет | Конфигурация | Время |
|---|---|---|---|---:|
| [`method3_judge.ipynb`](method3_judge.ipynb) | LLM-судья (Qwen2.5-7B) | Г1 разделение осей · Г2 self-consistency · Г3 пофрагментная верификация · H5 GEPA · H1 fine-tuning | `g2.1` (A100 80 GB) | 2 ч в ноутбуке + ~15 ч в Jobs |
| [`method6_grounding.ipynb`](method6_grounding.ipynb) | NLI-grounding (mDeBERTa) | H4 сигнал на faithfulness против relevance · абляция NLI-модели · вклад в стэк | любая GPU, идёт и на CPU | ~15 мин |

## Чем это отличается от `notebooks/*.ipynb`

Соседний контур (`00_setup`, `10_score_judge`, `20_train_encoder`, `30_finetune_judge`,
`40_verify_cli`) — **пусковые установки**: ячейка не считает ничего, только вызывает
CLI. Правило закреплено тестами и обосновано воспроизводимостью: расчёт, живущий в
ячейке, не попадает ни в `run.yaml`, ни в git-хэш.

Здесь задача другая — объяснить метод. Поэтому:

- **видно в ячейках:** промпты судьи и их версии, чеклист маркеров, формулы признаков
  grounding и coverage, извлечение вероятностей, все метрики и их доверительные
  интервалы, вердикты по гипотезам;
- **идёт через CLI:** корпусные прогоны (`scripts/run_m3.py`,
  `scripts/score_m6_grounding.py`) и оценка (`scripts/evaluate_cv.py`). Им нужны
  `--resume`, кэш судьи и `run.yaml` с git-хэшем рядом с артефактом — в ячейке этого
  не воспроизвести.

Формулы, показанные в ячейке метода 6, сверяются с `methods/m6/grounding.py`
ассертом: ноутбук не имеет права объяснять не тот метод, которым посчитаны числа.

Общее с соседним контуром — то, что нарушать нельзя: разбиение читается **только** из
`data/splits/folds_alfa.json`, `split_samples` не вызывается, каждое число идёт с 95%
доверительным интервалом. Это проверяет [`tests/test_standalone_notebooks.py`](../../tests/test_standalone_notebooks.py).

## Порядок запуска

Ноутбуки независимы: каждый сам клонирует репозиторий, ставит стек и поднимает всё,
что ему нужно. `00_setup.ipynb` для них не требуется.

**Метод 6** — просто Run All. Полный прогон по 2233 кейсам занимает около трёх минут
на A100 и около десяти на T4.

**Метод 3** — Run All до раздела H5. Ноутбук поднимает vLLM с `--max-logprobs 25` и
упирается в обязательный смоук на logprobs: пять кейсов, два ассерта. Красный ассерт
здесь означает, что извлечение вероятностей вырождено и полный прогон запускать
бессмысленно — он отработает без ошибок и не будет нести сигнала.

Дальше идут прогоны Г0–Г3 (в сумме около двух часов) и два раздела, которые уходят в
DataSphere Jobs, потому что длиннее двух часов, а VM ноутбука останавливается при
простое:

```
datasphere project job execute -p <project-id> -c jobs/gepa_markers_seed0.yaml   # H5, 6 заданий
datasphere project job execute -p <project-id> -c jobs/ft_judge_fold0.yaml       # H1, 5 заданий
```

Ноутбук печатает эти команды сам и умеет продолжить с того места, где задания
положили артефакты: ячейки после них проверяют наличие файлов и пропускают шаг, если
задание ещё считает. Итоговая таблица собирается по тем прогонам, которые готовы.

## Куда всё пишется

```
predictions/alfa/m3_judge/<вариант>/{scores.jsonl, report.json, run.yaml}
predictions/alfa/ft_judge/direct_fold<k>/{scores.jsonl, ft_diagnostics.json}
predictions/alfa/m6_grounding/<вариант>/{scores.jsonl, report.json, auc.json, run.yaml}
results/gepa/h5_markers_vs_plain.{md,json}
```

`scores.jsonl` — непрерывные признаки, без бинаризации: порог подбирает
`evaluate_cv.py` внутри train-части фолда. `report.json` без 95% ДИ не собирается —
это запрещает схема `EvaluationReport`.

Сводка того, что уже измерено, — [`docs/report/methods_3_6_results.md`](../../docs/report/methods_3_6_results.md).
